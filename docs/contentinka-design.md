# contentINKA — минимальная версия. Архитектура и решения

Рабочий документ по проектированию contentINKA — модуля автоматического отбора
и подготовки контента из фото тату-сессии. Фиксирует решения, принятые в
обсуждении, чтобы не терять контекст между итерациями.

## Топология

Три равноправных узла, а не «бот + придаток»:

```
        ┌─────────────┐
        │   Дневник   │   ← система записи: клиенты, сессии, карточки, история
        └──┬───────┬──┘
           │       │
   ┌───────▼──┐ ┌──▼────────┐
   │ Админка  │ │ ContentINKA│
   │ бота     │ │ (третий,   │
   │(Telegram)│ │ независимый│
   │          │ │  сервис)   │
   └──────────┘ └────────────┘
```

- **Дневник** — браузерное приложение мастера, держит всю базу (клиенты,
  сессии, карточки). Источник истины.
- **Админка бота (этот репозиторий, inka-bot)** — Telegram-канал для клиента
  и коротких рабочих команд Ани. К contentINKA отношения не имеет —
  фото-пайплайн НЕ встраивается в бота.
- **ContentINKA** — отдельный лёгкий сервис (свой бэкенд, без копии базы
  клиентов). Общается с Дневником через тот же паттерн, что уже используется
  в inka-bot: bridge-эндпоинт с секретом в заголовке (см. `pages/api/diary-sync.ts`
  как референс-пример).
  - Дневник → ContentINKA: контекст сессии (client/work/zone/style/description)
    + медиа-файлы.
  - ContentINKA → Дневник: размеченные и подтверждённые материалы,
    записываются обратно в карточку сессии.

ContentINKA не хранит копию клиентской базы — получает контекст сессии в
каждом запросе и хранит только то, что относится к процессу отбора (сами
медиа/ссылки, технические метрики, оценки модели, статус подтверждения).

## Слой 1 — «Куратор» (объём минимальной версии)

### Входные данные v1
- **Фото** — да, с самого начала.
- **Видео** — отложено на потом (решение зафиксировано). Пайплайн для фото
  спроектирован так, чтобы видео можно было добавить отдельным техническим
  фильтром позже, не переделывая классификацию.

### Пайплайн

**1. Технический отбор (детерминированный, без модели)**
- phash → дубли/почти-дубли.
- sharpness-метрика → расфокус/смаз/слабые кадры.
- Детект depth-данных (Portrait mode на iPhone, EXIF/метаданные) →
  флаг `has_depth_data`. Не отдельная категория, а бонус-сигнал для
  `quality_score` на шаге 2: такой кадр гибче (фокус можно пересобрать
  постфактум), это повышает оценку, но не меняет `role`.
- Результат: kept/rejected + причина, доступно мастеру для «вернуть».

**2. Классификация (один LLM vision-вызов на сессию)**
Вход — выжившие фото + контекст сессии из Дневника. На каждое фото модель
возвращает:
- `role` — общий вид / деталь / процесс / финал;
- `quality_score` — оценка визуального качества (композиция, свет, ракурс,
  читаемость тату, депф-бонус), отдельно от техотбора шага 1;
- `cover_candidate` — булев флаг;
- `format` — пост / сторис. Без видео формат «рилс» в v1 не используется.
  Формат — не отдельное жёсткое правило, а производная от `role` +
  `quality_score` в том же вызове (сильный role + высокий quality → пост;
  слабее — сторис).

Полная система архетипов вынесена в отдельный документ:
[`contentinka-archetypes.md`](./contentinka-archetypes.md). Кратко: правило
не «1 открывает / 2 ведёт / 3 закрывает / 4 через визуал», а **1 визуальный
архетип + текстовая триада из 3 архетипов** (Трикстер, Женщина, Исследователь,
Мудрец, Дурак, Lover, Творец — у каждого своя функция, свет, тень и правила
передачи друг другу). Визуальный архетип выбирается отдельно от текстовой
триады и не обязан с ней совпадать — фото говорит собственным голосом (поза,
свет, дистанция, цвет, фактура), а не иллюстрирует текст.

**3. Текст-черновики (LLM-текстовый проход)**
Перед генерацией текста фиксируется внутренняя разметка (не публикуется):
цель материала, визуальный архетип фото, текстовая триада с ролями —
кто открывает / кто ведёт / кто закрывает (полная логика выбора триады и
контроль ухода в тень — см. `contentinka-archetypes.md`, §3, §9, §10). На
основе этой разметки — черновик подписи на каждый отобранный материал (или
на группу — для карусели). Голос бренда (мастер пришлёт отдельно) встраивается
как ещё один блок контекста в этот проход, по аналогии с тем, как
`adminPrompt.txt` уже описывает тон Инки. Тема может быть переопределена
мастером текстом на входе — тогда она перекрывает дефолтную цель материала,
но структура триады (кто открывает/ведёт/закрывает) выбирается заново под
эту тему, а не наследуется механически.

**4. Финальный фильтр архетипов**
Перед выдачей материала — проверка по чек-листу `contentinka-archetypes.md`
§11 (одна ясная цель, один визуальный архетип, текстовая триада с понятными
ролями, ни один архетип не ушёл в тень, фото говорит своим голосом, а не
иллюстрирует текст). Если архетип ушёл в тень — не добавляется архетип
поверх, а обрезается лишнее и возвращается исходная функция.

**5. Подтверждение — окно внутри Дневника**
Не отдельный интерфейс и не Telegram. Одно окно, встроенное в карточку
сессии Дневника:
- **Основная зона** — готовый пакет, сгруппированный по `role`, внутри —
  по качеству: отличные / хорошие / на доработку / отбракованные
  (отбраковка = результат шага 1, три остальных — пороги по
  `quality_score` из шага 2). Готовые пост(ы) с текстом и сторис лежат
  здесь же.
- **Ручная панель** — отдельно: поле ввода текста + загрузка своих фото,
  чтобы собрать и сгенерировать пост напрямую, в обход автоматического
  отбора (тот же текстовый проход шага 3, но на явно заданном наборе, без
  техфильтра и без архетип-подбора).
- **Открытие фото в нативном хранилище (iPhone)** — технически невозможно
  для браузерного приложения: iOS не даёт веб-страницам диплинк в Photos
  на конкретный asset (песочница платформы, обхода нет). Доступная
  альтернатива — кнопка «скачать оригинал». Диплинк в нативную галерею
  потребовал бы нативного (не браузерного) приложения — не в рамках
  текущей архитектуры.

### API-контракт (черновой)

Дневник → ContentINKA (`POST /ingest`, `Authorization: Bearer <секрет>`):
```json
{
  "session": {
    "client": "...", "work": "...", "zone": "...",
    "style": "...", "description": "..."
  },
  "media": [{ "id": "...", "url": "..." }],
  "text_topic": null
}
```

ContentINKA → Дневник (ответ / callback после подтверждения):
```json
{
  "media": [{
    "id": "...", "technical_status": "kept",
    "role": "detail", "quality_score": 0.78,
    "has_depth_data": true, "cover_candidate": false,
    "format": "post", "order_index": 3,
    "visual_archetype": "lover",
    "text_triad": { "opens": "explorer", "leads": "sage", "closes": "fool" },
    "text_draft": "...", "master_decision": "pending"
  }]
}
```

Внутренняя карточка разметки (цель материала, состояние зрителя до/после,
риск ухода в тень — формат см. `contentinka-archetypes.md` §10) в этот ответ
не входит; она хранится в ContentINKA и показывается мастеру только по
запросу «объясни механику».

## Слой 2 — «Менеджер» (стратег + тактик) — вне минимальной версии

Роль: не разовая оценка сессии, а рассуждение поперёк времени — что уже
опубликовано, в каком темпе, каких форматов/архетипов давно не было. Требует
отдельного состояния (история публикаций: формат, archetype, дата) — сейчас
в системе такого хранилища нет, это первое, что понадобится завести перед
проектированием Менеджера.

Решение по режиму работы: **советчик, не исполнитель** — предлагает ход
(«сделай рилс, процессов не было две недели»), финальное решение и публикация
остаются за мастером. Совпадает с исходным ограничением — публикацию не
трогаем.

Порядок: Слой 2 не проектируется, пока Слой 1 не проверен на реальных
сессиях — стратегия не должна строиться поверх непроверенной разметки.

## Открытые вопросы
- Бренд-войс / модель настроения для текста — ожидается от мастера,
  будет встроена в шаг 3 как контекстный блок промпта.
- Видео — технический фильтр и формат «рилс» проектируются отдельным
  этапом, когда видео возвращается в scope.
