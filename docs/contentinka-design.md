# contentINKA — минимальная версия. Архитектура и решения

Рабочий документ по проектированию contentINKA — модуля автоматического отбора
и подготовки контента из фото тату-сессии. Фиксирует решения, принятые в
обсуждении, чтобы не терять контекст между итерациями.

## Топология

Три равноправных узла, а не «бот + придаток»:

```
        ┌─────────────┐
        │   Дневник   │   ← система записи: клиенты, сессии, карточки, история
        └──┬───────┬──┘
           │       │
   ┌───────▼──┐ ┌──▼────────┐
   │ Админка  │ │ ContentINKA│
   │ бота     │ │ (третий,   │
   │(Telegram)│ │ независимый│
   │          │ │  сервис)   │
   └──────────┘ └────────────┘
```

- **Дневник** (репозиторий `dnevnik-mastera`) — держит всю базу (клиенты,
  сессии, карточки), но **не имеет собственного бэкенда**: это чистое
  браузерное SPA (Vite + React), вся база живёт в IndexedDB прямо на
  устройстве мастера. С ботом он уже сегодня общается напрямую из браузера
  (`src/lib/calendarSync.ts` → `pages/api/diary-sync.ts`): fire-and-forget
  fetch с секретом из localStorage, CORS open на стороне бота. Это и есть
  референс-паттерн для интеграции с ContentINKA — не сервер-сервер, а
  браузер-сервер.
- **Админка бота (этот репозиторий, inka-bot)** — Telegram-канал для клиента
  и коротких рабочих команд Ани. К contentINKA отношения не имеет —
  фото-пайплайн НЕ встраивается в бота.
- **ContentINKA** — отдельный лёгкий сервис (свой бэкенд, без копии базы
  клиентов). Дневник обращается к нему **прямо из браузера**, тем же
  паттерном, что уже используется для календаря: bridge-эндпоинт с секретом
  в заголовке, свой localStorage-ключ для настроек (по аналогии с
  `inka-calendar-sync`).
  - Дневник → ContentINKA: контекст сессии (client/work/zone/style/description)
    + фото.
  - ContentINKA → Дневник: размеченные материалы — ответ на тот же fetch,
    Дневник сохраняет его в IndexedDB как часть карточки сессии.

ContentINKA не хранит копию клиентской базы — получает контекст сессии в
каждом запросе и хранит только то, что относится к процессу отбора (сами
медиа/ссылки, технические метрики, оценки модели, статус подтверждения).

**Фото уже есть как готовая фича Дневника.** У `Session` уже есть поле
`photos: string[]` (base64 data URL, компонент `SessionPhotos`,
`updateSessionPhotos`) — мастер загружает фото прямо в карточку сессии уже
сейчас, безо всякого contentINKA. Новую загрузку строить не нужно —
ContentINKA подключается к уже существующим данным. Поле `Session.done`
(флаг завершённости) — естественная точка триггера «сессия закончена, можно
отправлять на отбор».

**Маппинг контекста сессии** (реальные поля из `Client`/`Session` в
`TattoDiary.tsx`, а не абстракция):
- `client` = `${client.name} ${client.surname}`;
- `work` = `session.name` (заголовок сессии, напр. «Голубика»);
- `zone` = `session.area`;
- `style` = `session.style`;
- `description` = `session.note`.

**Размер запроса — решено через превью, не через дробление на фото.** Фото
в Дневнике хранятся как base64 data URL — удобно для IndexedDB, но один
такой файл легко весит несколько МБ, а serverless-функции (Vercel) по
умолчанию режут тело запроса на ~4.5 МБ. Дробить классификацию на
запрос-на-фото было бы проще технически, но **ломает саму задачу шага 2**:
роль (общий вид/деталь/финал), `cover_candidate` и выбор триады — решения
относительные, модель должна видеть все фото сессии разом, чтобы сравнить
их между собой, а не судить каждое в вакууме.

Вместо этого — **сжатые превью, отправленные батчем**. Перед отправкой
Дневник даунсайзит каждое фото на клиенте (canvas resize до ~512–768px по
длинной стороне) — превью весит десятки-сотни КБ вместо мегабайт, вся
сессия из 20–30 таких превью укладывается в лимит одним запросом. Оригиналы
(полный base64 из `session.photos`) нужны только для показа/скачивания в
самом Дневнике — модели на вход не идут.

## Слой 1 — «Куратор» (объём минимальной версии)

### Входные данные v1
- **Фото** — да, с самого начала.
- **Видео** — отложено на потом (решение зафиксировано). Пайплайн для фото
  спроектирован так, чтобы видео можно было добавить отдельным техническим
  фильтром позже, не переделывая классификацию.

### Пайплайн

**1. Технический отбор (детерминированный, без модели)**
- phash → дубли/почти-дубли.
- sharpness-метрика → расфокус/смаз/слабые кадры.
- Детект depth-данных (Portrait mode на iPhone, EXIF/метаданные) →
  флаг `has_depth_data`. Не отдельная категория, а бонус-сигнал для
  `quality_score` на шаге 2: такой кадр гибче (фокус можно пересобрать
  постфактум), это повышает оценку, но не меняет `role`.
- Результат: kept/rejected + причина, доступно мастеру для «вернуть».

**Скриншоты/захваты кадра из видео — не повод отбраковывать.** Мастер
осознанно использует стоп-кадры из видео как источник фото — техфильтр не
должен резать их по признаку «это скриншот». Проблема — не в происхождении
кадра, а в **интерфейсном мусоре поверх изображения** (водяной знак
редактора, кнопки плеера, таймлайн-полоса), если он есть. Это нельзя
надёжно поймать дешёвой детерминированной проверкой (в отличие от
phash/blur) — такой кадр технически резкий и не дубль, просто на нём
чужой UI. Ловится на шаге 2 (классификация), где модель и так смотрит на
содержимое: если видит элементы интерфейса поверх кадра — возвращает
`technical_status: "rejected"` с причиной `"ui_overlay"`, а не через
шаг 1.

**2. Классификация (один LLM vision-вызов на сессию)**
Вход — выжившие фото + контекст сессии из Дневника. На каждое фото модель
возвращает:
- `role` — общий вид / деталь / процесс / финал;
- `quality_score` — оценка визуального качества (композиция, свет, ракурс,
  читаемость тату, депф-бонус), отдельно от техотбора шага 1;
- `cover_candidate` — булев флаг;
- проверка на UI-мусор поверх кадра (см. выше) — если есть, `role`/`format`
  не назначаются, кадр уходит в `rejected`;
- `format` — пост / сторис. Без видео формат «рилс» в v1 не используется.
  Формат — не отдельное жёсткое правило, а производная от `role` +
  `quality_score` в том же вызове (сильный role + высокий quality → пост;
  слабее — сторис).

Полная система архетипов вынесена в отдельный документ:
[`contentinka-archetypes.md`](./contentinka-archetypes.md). Кратко: правило
не «1 открывает / 2 ведёт / 3 закрывает / 4 через визуал», а **1 визуальный
архетип + текстовая триада из 3 архетипов** (Трикстер, Женщина, Исследователь,
Мудрец, Дурак, Lover, Творец — у каждого своя функция, свет, тень и правила
передачи друг другу). Визуальный архетип выбирается отдельно от текстовой
триады и не обязан с ней совпадать — фото говорит собственным голосом (поза,
свет, дистанция, цвет, фактура), а не иллюстрирует текст.

**3. Текст-черновики (LLM-текстовый проход)**
Перед генерацией текста фиксируется внутренняя разметка (не публикуется):
цель материала, визуальный архетип фото, текстовая триада с ролями —
кто открывает / кто ведёт / кто закрывает (полная логика выбора триады и
контроль ухода в тень — см. `contentinka-archetypes.md`, §3, §9, §10). На
основе этой разметки — черновик подписи на каждый отобранный материал (или
на группу — для карусели). Тон, которым говорит триада, задаёт голос бренда
Inkanya — зафиксирован в [`contentinka-brand-voice.md`](./contentinka-brand-voice.md)
(ядро голоса, ритм, словарь и стоп-слова, тепло/дерзость/юмор без ухода в
тень, голос по форматам пост/сторис/рилс/реклама/ответ клиенту/цена,
финальный фильтр). Этот документ — постоянный контекстный блок шага 3, по
аналогии с тем, как `adminPrompt.txt` уже описывает тон Инки в боте. Тема
может быть переопределена мастером текстом на входе — тогда она перекрывает
дефолтную цель материала, но структура триады (кто открывает/ведёт/закрывает)
выбирается заново под эту тему, а не наследуется механически, и брендвойс
применяется всегда, независимо от темы.

**4. Финальный фильтр**
Перед выдачей материала — два чек-листа подряд: `contentinka-archetypes.md`
§11 (одна ясная цель, один визуальный архетип, текстовая триада с понятными
ролями, ни один архетип не ушёл в тень, фото говорит своим голосом, а не
иллюстрирует текст) и `contentinka-brand-voice.md` §15 (звучит как живой
мастер, а не бренд-менеджер; тепло не липкое; дерзость не унижает;
экспертность не лекция; юмор не клоунада; один понятный CTA; слышна Аня).
Если архетип ушёл в тень или текст не проходит brand-voice фильтр — не
добавляется правка поверх, а обрезается лишнее и возвращается исходная
функция/тон.

**5. Подтверждение — окно внутри Дневника**
Не отдельный интерфейс и не Telegram. Одно окно, встроенное в карточку
сессии Дневника:
- **Основная зона** — готовый пакет, сгруппированный по `role`, внутри —
  по качеству: отличные / хорошие / на доработку / отбракованные
  (отбраковка = результат шага 1, три остальных — пороги по
  `quality_score` из шага 2). Готовые пост(ы) с текстом и сторис лежат
  здесь же.
- **Ручная панель** — отдельно: поле ввода текста + загрузка своих фото,
  чтобы собрать и сгенерировать пост напрямую, в обход автоматического
  отбора (тот же текстовый проход шага 3, но на явно заданном наборе, без
  техфильтра и без архетип-подбора).
- **Строка коммуникации с моделью** — у каждого уже готового материала
  (не только в ручной панели) свободное текстовое поле для инструкции
  contentINKA, не создание с нуля, а правка/диалог по существующему
  результату. Три типовых сценария:
  - **смена тона/архетипов** — «сделай теплее», «смени триаду на
    Мудрец-Дурак-Творец» — перегенерирует текст (шаг 3) с тем же фото и
    целью, но новой триадой/тоном;
  - **просьба объяснить механику** — «почему это рилс, а не пост» —
    показывает внутреннюю карточку разметки (см.
    `contentinka-archetypes.md` §10: цель, визуальный архетип, триада,
    риск ухода в тень), которая иначе мастеру не показывается;
  - **свободный запрос** — «допиши ещё вариант текста», «а если через
    Lover» — общий диалог по аналогии с `mode = "dialog"` в `admin.ts`,
    только контекст — не клиент, а конкретный материал сессии.
  Технически это не новый пайплайн, а один и тот же вызов классификации/
  текста (шаги 2–3) с доп. полем `master_instruction`, привязанным к
  конкретному `media.id`.
- **Найти оригинал на телефоне — решено через EXIF-время, не через диплинк.**
  Прямой переход в приложение «Фото» на конкретный снимок технически
  невозможен для веб-страницы (песочница iOS, обхода нет), и обычное имя
  файла тоже не помогает — в Фото нет поиска по имени, только по
  дате/месту/содержимому. Рабочее решение: при загрузке фото в
  `SessionPhotos` парсить EXIF `DateTimeOriginal` из байтов файла (уже
  доступны через `FileReader`, нужна лёгкая JS-библиотека для чтения
  EXIF — в `dnevnik-mastera` её пока нет, надо добавить) и показывать точное
  время съёмки рядом с превью. По этому времени мастер сама находит кадр в
  Фото за секунды (поиск по дате или прокрутка ленты, которая всегда
  отсортирована по дате съёмки). Если EXIF отсутствует (скриншот, фото
  прошло через мессенджер с агрессивным сжатием) — поле просто не
  показывается, без ошибки. Кнопка «скачать оригинал» (из сохранённого
  base64) остаётся как запасной вариант независимо от EXIF.

### API-контракт (актуальный, сверен с реальным кодом Дневника)

Полный контракт с примерами запросов/ответов — в
[`contentinka-diary-handoff.md`](./contentinka-diary-handoff.md). Ключевое
отличие от раннего черновика: у Дневника нет бэкенда и нет URL для фото
(`session.photos` в `TattoDiary.tsx` — base64 data URL в IndexedDB), значит
фото передаются прямо в теле запроса. Но передаются **сжатыми превью
батчем на всю сессию**, не по одному оригиналу за запрос — иначе
классификация теряет возможность сравнивать фото между собой (см. выше):

- `POST /ingest` — Дневник даунсайзит все фото сессии до превью на клиенте
  и шлёт их одним запросом вместе с контекстом сессии; в ответ — разметка
  каждого фото (role/quality/format/visual_archetype/text_triad/text_draft)
  и порядок (`order_index`, 4-й архетип/ритм) — уже с учётом всей сессии
  разом, не отдельным шагом. Вызывается при завершении сессии
  (`session.done`).
- `POST /media/{media_id}/instruct` — строка коммуникации с моделью:
  Дневник повторно шлёт `session` + превью нужного фото (ContentINKA не
  хранит состояние между вызовами) + `master_instruction`; в ответ —
  обновлённая разметка, и опционально `internal_card`, если мастер просила
  объяснить механику.

Дневник обращается ко всем эндпоинтам **напрямую из браузера**, тем же
паттерном, что уже работает для календаря (`calendarSync.ts` →
`diary-sync.ts`): fetch с `Authorization: Bearer <секрет>`, секрет — в
своём ключе localStorage, CORS open на стороне ContentINKA.

Внутренняя карточка разметки (цель материала, состояние зрителя до/после,
риск ухода в тень — формат см. `contentinka-archetypes.md` §10) в этот ответ
не входит; она хранится в ContentINKA и показывается мастеру только по
запросу «объясни механику».

## Слой 2 — «Менеджер» (стратег + тактик) — вне минимальной версии

Роль: не разовая оценка сессии, а рассуждение поперёк времени — что уже
опубликовано, в каком темпе, каких форматов/архетипов давно не было. Требует
отдельного состояния (история публикаций: формат, archetype, дата) — сейчас
в системе такого хранилища нет, это первое, что понадобится завести перед
проектированием Менеджера.

Решение по режиму работы: **советчик, не исполнитель** — предлагает ход
(«сделай рилс, процессов не было две недели»), финальное решение и публикация
остаются за мастером. Совпадает с исходным ограничением — публикацию не
трогаем.

Порядок: Слой 2 не проектируется, пока Слой 1 не проверен на реальных
сессиях — стратегия не должна строиться поверх непроверенной разметки.

## Открытые вопросы
- Видео — технический фильтр и формат «рилс» проектируются отдельным
  этапом, когда видео возвращается в scope.
- Порог сжатия превью (512 vs 768px, качество JPEG) — подобрать эмпирически:
  достаточно для того, чтобы модель различала детали/фактуру/depth-сигнал,
  но не настолько большим, чтобы упереться в лимит тела запроса на сессиях
  с 25-30+ фото.
- Промпт шага 2 (классификация) не проверен на реальных фото — см.
  `contentinka-classification-prompt.md`, нужно прогнать вручную перед тем,
  как писать код эндпоинта.
- Реализация обеих сторон bridge теперь возможна из этой сессии — репозиторий
  `dnevnik-mastera` подключён (`/workspace/dnevnik-mastera`), можно писать
  код интеграции на стороне Дневника напрямую, а не только контракт.
