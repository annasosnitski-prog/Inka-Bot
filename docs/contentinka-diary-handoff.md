# ContentINKA ↔ Дневник — что нужно реализовать на стороне Дневника

Памятка для разработчика Дневника (`dnevnik-mastera`): что именно нужно,
чтобы Дневник мог отдавать фото сессии в ContentINKA и получать обратно
готовую подборку. ContentINKA — отдельный сервис; Дневник обращается к нему
**напрямую из браузера**, не через какой-то свой сервер — у Дневника нет
бэкенда, это чистое SPA (Vite + React), вся база в IndexedDB на устройстве.
Паттерн ровно тот же, что уже работает для календаря: `src/lib/calendarSync.ts`
шлёт fetch из браузера в `pages/api/diary-sync.ts` (бот), с секретом из
localStorage и открытым CORS на принимающей стороне. ContentINKA нужно
встраивать так же.

## Что уже есть в Дневнике и не нужно строить заново

- **Фото уже загружаются.** `Session.photos: string[]` — компонент
  `SessionPhotos` (`TattoDiary.tsx`), фото читаются через `FileReader` и
  хранятся как **base64 data URL**, не файлы на диске и не URL. Апдейтит их
  `updateSessionPhotos(sessionId, photos)`. Новую загрузку изобретать не
  нужно — ContentINKA цепляется к этому же полю.
- **Триггер «сессия завершена» уже есть.** `Session.done: boolean`. Логичная
  точка для вызова ContentINKA — переход `done: false → true` (или отдельная
  кнопка «отправить в контент», решается по месту).
- **Контекст сессии — реальные поля**, не абстракция:
  - `client` = `${client.name} ${client.surname}` (из родительского `Client`);
  - `work` = `session.name`;
  - `zone` = `session.area`;
  - `style` = `session.style`;
  - `description` = `session.note`.

## Что нужно добавить

1. **Новый модуль по образцу `calendarSync.ts`** — например
   `src/lib/contentSync.ts`: настройки (`enabled`, `endpoint`, `secret`) в
   своём ключе localStorage (не `inka-calendar-sync`, отдельный — например
   `inka-content-sync`), fetch к ContentINKA с `Authorization: Bearer
   <секрет>`.
2. **Вызов при завершении сессии** — отправка `session.photos` +
   контекст (см. выше) в ContentINKA.
3. **Хранение ответа** — новое поле на `Session` (например
   `contentDraft: ContentMedia[] | null`) для результата классификации;
   рисуется как окно/вкладка «Контент» внутри карточки сессии (готовый
   пакет по роли/качеству, ручная панель, строка коммуникации с моделью —
   см. `contentinka-design.md`).
4. **Отправка инструкций мастера** — при вводе текста в строку
   коммуникации у материала — вызов на ContentINKA с ссылкой на конкретный
   `media.id`.

Решение «оставить/убрать/вернуть» кадр (`master_decision`) хранится только в
`Session.contentDraft` на стороне Дневника — ContentINKA этого решения
обратно не требует для минимальной версии.

## Важно: фото — это base64, не URL

У Дневника нет сервера, значит нет и стабильного URL, по которому
ContentINKA могла бы сама скачать фото. **Фото передаются целиком в теле
запроса как data URL**, а не ссылкой. Это меняет форму `/ingest` по
сравнению с более ранним черновиком контракта.

**Риск размера запроса.** Один data URL легко весит несколько МБ, в сессии
может быть десятки фото. Serverless-функции (Vercel, судя по всему хостинг
и бота, и, вероятно, ContentINKA) по умолчанию режут тело запроса на
~4.5 МБ. Поэтому классификация должна идти **по одному фото за запрос**, а
не пачкой на всю сессию:

## Эндпоинт 1 — `POST /ingest/media`

Вызывается один раз на каждое фото в `session.photos` при завершении
сессии (Дневник сам итерирует по массиву и шлёт N запросов, не один
большой).

**Запрос:**
```json
{
  "session_id": "diary-session-id",
  "session": {
    "client": "Александра",
    "work": "Голубика",
    "zone": "Левое плечо",
    "style": "минимализм",
    "description": "..."
  },
  "media_id": "photo-index-or-hash",
  "photo_data_url": "data:image/jpeg;base64,..."
}
```
- `session_id` — id сессии в Дневнике, чтобы ContentINKA могла (если
  понадобится) сопоставлять фото одной сессии между собой при повторных
  вызовах — сама она сессию не хранит, это просто сквозной идентификатор.
- `media_id` — любой стабильный идентификатор конкретного фото на стороне
  Дневника (например индекс в массиве `photos` или хэш содержимого), чтобы
  потом сопоставить ответ с конкретным элементом `session.photos`.

**Ответ:**
```json
{
  "media_id": "photo-index-or-hash",
  "technical_status": "kept",
  "role": "detail",
  "quality_score": 0.78,
  "has_depth_data": true,
  "cover_candidate": false,
  "format": "post",
  "visual_archetype": "lover",
  "text_triad": { "opens": "explorer", "leads": "sage", "closes": "fool" },
  "text_draft": "...",
  "master_decision": "pending"
}
```

`order_index` (порядок внутри подборки, шаг 4-й архетип/ритм) в ответ на
отдельное фото не входит — это решение принимается по всей сессии сразу,
после того как Дневник собрал ответы по всем фото. Если понадобится —
отдельный лёгкий эндпоинт `POST /sequence` на массив уже полученных
`media_id` + `role`/`quality_score`, возвращающий порядок. Для минимальной
версии можно отложить и сортировать в Дневнике по умолчанию (role → quality).

Отклонённые на техническом этапе фото тоже возвращаются с
`technical_status: "rejected"` (и причиной) — чтобы мастер могла нажать
«вернуть».

## Эндпоинт 2 — `POST /media/{media_id}/instruct`

Вызывается, когда мастер пишет инструкцию к конкретному уже готовому
материалу. Тело запроса должно повторно включать `photo_data_url` и
`session` — ContentINKA ничего не хранит между вызовами, поэтому не может
восстановить фото сама по `media_id`.

**Запрос:**
```json
{
  "session": { "client": "...", "work": "...", "zone": "...", "style": "...", "description": "..." },
  "photo_data_url": "data:image/jpeg;base64,...",
  "master_instruction": "смени триаду на Мудрец-Дурак-Творец"
}
```

**Ответ** — обновлённый объект (тот же формат, что из `/ingest/media`),
плюс опционально `internal_card`, если инструкция была просьбой объяснить
механику, а не перегенерировать:
```json
{
  "media": { "...": "как выше, с обновлённым text_draft/triad" },
  "internal_card": {
    "goal": "...",
    "viewer_state_before": "...",
    "viewer_state_after": "...",
    "visual_archetype": "lover",
    "text_triad": { "opens": "...", "leads": "...", "closes": "..." },
    "shadow_risk": "..."
  }
}
```
`internal_card` в интерфейсе показывается только когда мастер сама
попросила — по умолчанию скрыта.

## Глоссарий полей (для UI Дневника)

- `technical_status` — `kept` / `rejected` (дубль или расфокус).
- `role` — `overview` / `detail` / `process` / `final`.
- `quality_score` — 0–1, визуальное качество кадра.
- `has_depth_data` — есть depth/Portrait-данные (iPhone) — кадр гибче.
- `cover_candidate` — годится в обложку.
- `format` — `post` / `story` (без видео `reel` в v1 не используется).
- `visual_archetype` — какой архетип говорит через фото (один из семи).
- `text_triad` — три архетипа текста с ролями `opens`/`leads`/`closes`.
- `text_draft` — готовый черновик подписи.
- `master_decision` — `pending` / `confirmed` / `removed` — управляется и
  хранится Дневником, ContentINKA не читает и не пишет это поле.

Названия архетипов и логика голоса бренда — справочно, если понадобится
контекст: `contentinka-archetypes.md`, `contentinka-brand-voice.md` в
репозитории `inka-bot`. Для интеграции сама философия не нужна — только
контракт полей выше.

## Что пока не решено

- Тайм-аут на фото: vision-классификация одного фото может занимать
  секунды-десятки секунд. При N фото на сессию и последовательных вызовах
  «завершить сессию» может подвиснуть на UI — стоит слать запросы
  параллельно (с разумным лимитом одновременных) и показывать прогресс
  «обработано X из N», а не ждать всё разом.
- `POST /sequence` (порядок кадров, 4-й архетип/ритм) — вынесен как
  отдельный опциональный шаг, не обязателен для первой версии.
