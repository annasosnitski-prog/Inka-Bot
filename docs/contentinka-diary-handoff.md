# ContentINKA ↔ Дневник — что нужно реализовать на стороне Дневника

Памятка для разработчика Дневника: что именно нужно, чтобы Дневник мог
отдавать фото сессии в ContentINKA и получать обратно готовую подборку.
ContentINKA — отдельный сервис, Дневник обращается к нему как клиент (тем же
паттерном, каким сейчас Дневник уже пишет в календарь бота через
`diary-sync`, только в обратную сторону: здесь Дневник — вызывающая
сторона).

## Что нужно со стороны Дневника

1. **Хостинг фото по URL.** ContentINKA не хранит копию фото — она получает
   ссылку и обращается по ней сама (в том числе повторно, если понадобится
   пересчёт). Значит, фото, загруженные мастером, должны быть доступны по
   стабильному URL (публичному или доступному серверу ContentINKA) на
   момент запроса.
2. **Триггер на «сохранить» после загрузки фото в карточку сессии** —
   вызов `POST /ingest` (см. ниже) со списком загруженных фото и данными
   карточки сессии.
3. **Хранение ответа** — записать то, что вернёт ContentINKA (роль,
   качество, формат, архетипы, текст-черновик), в поле карточки сессии, и
   отрисовать окно подтверждения (готовый пакет, сгруппированный по роли и
   качеству — см. дизайн ниже).
4. **Отправка инструкций мастера** — когда мастер пишет в строку
   коммуникации у конкретного материала («сделай теплее», «почему это
   рилс», «допиши вариант») — вызов `POST /media/{id}/instruct`.
5. **Секрет для авторизации** — свой собственный (не тот, что уже
   используется для `diary-sync`), хранится в настройках Дневника и
   подставляется в заголовок `Authorization: Bearer <секрет>` при каждом
   вызове.

Решение «оставить/убрать/вернуть» кадр (`master_decision`) можно хранить
только в самой карточке Дневника — ContentINKA этого решения обратно не
требует для минимальной версии, ей не нужно знать финальный выбор мастера.

## Эндпоинт 1 — `POST /ingest`

Вызывается, когда мастер загрузила фото в завершённую сессию и нажала
«сохранить».

**Запрос:**
```json
{
  "session": {
    "client": "Имя клиента",
    "work": "описание работы",
    "zone": "предплечье",
    "style": "минимализм / реализм / …",
    "description": "свободное описание сессии"
  },
  "media": [
    { "id": "diary-media-id-1", "url": "https://.../photo1.jpg" },
    { "id": "diary-media-id-2", "url": "https://.../photo2.jpg" }
  ],
  "text_topic": null
}
```
- `session.*` — те же поля, что уже есть в карточке сессии Дневника.
- `media[].id` — идентификатор фото на стороне Дневника (чтобы потом
  сопоставить ответ с конкретным файлом).
- `text_topic` — опционально, если мастер сразу задаёт тему для текста
  (иначе `null` — тема по умолчанию берётся из архетипов/brand-voice).

**Ответ:**
```json
{
  "media": [
    {
      "id": "diary-media-id-1",
      "technical_status": "kept",
      "role": "detail",
      "quality_score": 0.78,
      "has_depth_data": true,
      "cover_candidate": false,
      "format": "post",
      "order_index": 3,
      "visual_archetype": "lover",
      "text_triad": { "opens": "explorer", "leads": "sage", "closes": "fool" },
      "text_draft": "...",
      "master_decision": "pending"
    }
  ]
}
```

Отклонённые на техническом этапе фото тоже попадают в ответ с
`technical_status: "rejected"` (и причиной) — чтобы мастер могла нажать
«вернуть» на любое из них.

## Эндпоинт 2 — `POST /media/{id}/instruct`

Вызывается, когда мастер пишет инструкцию к конкретному уже готовому
материалу.

**Запрос:**
```json
{ "master_instruction": "смени триаду на Мудрец-Дурак-Творец" }
```

**Ответ** — обновлённый объект `media` (тот же формат, что в `/ingest`),
плюс опционально `internal_card`, если мастер просила объяснить механику,
а не перегенерировать:
```json
{
  "media": { "...": "как выше, с обновлённым text_draft/triad" },
  "internal_card": {
    "goal": "...",
    "viewer_state_before": "...",
    "viewer_state_after": "...",
    "visual_archetype": "lover",
    "text_triad": { "opens": "...", "leads": "...", "closes": "..." },
    "shadow_risk": "..."
  }
}
```
`internal_card` в интерфейсе показывается только когда мастер сама
попросила — по умолчанию скрыта.

## Глоссарий полей (для UI Дневника)

- `technical_status` — `kept` / `rejected` (дубль или расфокус).
- `role` — `overview` / `detail` / `process` / `final`.
- `quality_score` — 0–1, визуальное качество кадра.
- `has_depth_data` — есть depth/Portrait-данные (iPhone) — кадр гибче.
- `cover_candidate` — годится в обложку.
- `format` — `post` / `story` (без видео `reel` в v1 не используется).
- `order_index` — порядок кадра внутри подборки.
- `visual_archetype` — какой архетип говорит через фото (один из семи).
- `text_triad` — три архетипа текста с ролями `opens`/`leads`/`closes`.
- `text_draft` — готовый черновик подписи.
- `master_decision` — `pending` / `confirmed` / `removed` — управляется и
  хранится Дневником, ContentINKA не читает и не пишет это поле.

Названия архетипов и логика голоса бренда — справочно, если понадобится
контекст: `contentinka-archetypes.md`, `contentinka-brand-voice.md` в этом
репозитории (inka-bot). Разработчику Дневника для интеграции сама
философия не нужна — только контракт полей выше.

## Что пока не решено (спросить, если критично для реализации)

- Тайм-аут `/ingest`: классификация нескольких фото через vision-модель
  может занимать десятки секунд. Нужно решить на стороне Дневника — ждать
  синхронно с индикатором загрузки, или ContentINKA должен отвечать сразу
  и присылать результат отдельным callback/через поллинг. Для минимальной
  версии предполагается синхронный ответ с достаточным тайм-аутом (~60с).
- Хостинг фото — если у Дневника ещё нет стабильного публичного URL для
  загруженных файлов, это нужно решить до интеграции (см. пункт 1 выше).
