# Inka-Bot — карта проекта

Телеграм-бот для тату-мастера: ведёт клиента от первого сообщения до записи
(идея → место → размер → цена → телефон → даты), пишет мастеру, когда нужно
её внимание, и отдельно обслуживает саму мастера в admin-режиме (счета,
портреты клиентов, управление календарём).

Этот файл — не описание кода построчно, а карта "что где лежит и почему
именно так", чтобы не тратить полдня на реконструкцию решений по гит-истории.
Комментарии в самих файлах обычно объясняют "почему" подробнее — этот файл
только даёт, откуда начинать.

## Один ход диалога — главный файл `pages/api/telegram.ts`

Каждое сообщение клиента проходит один и тот же путь:

1. **Найти карточку(и) клиента** в Airtable по `telegram_id`. Обычно одна
   строка = один клиент, но клиент может вести **до двух** независимых
   проектов одновременно (см. ниже) — тогда решается, какую из них
   продолжает это сообщение.
2. **Extractor** (LLM) читает сообщение + карточку + недавнюю историю и
   возвращает факты (`idea`, `placement`, `price_quoted`...) и служебные
   сигналы этого хода (`service_fit`, `is_new_project_request`,
   `photo_purpose`...). Экстрактор **не решает, что ответить** — только
   извлекает.
3. **`mergeClientCard`** (`lib/clientCardMerge.ts`) сливает факты в карточку.
   Отдельно обрабатывает три случая: обычное продолжение, реально новый
   проект (сброс проектных полей, сохранение личных), новый проект при уже
   забронированном (карточку брони не трогать).
4. **`getNextStep`** (`lib/stateMachine.ts`) — чистая функция без LLM и без
   сети: по карточке + сигналам решает следующий шаг воронки
   (`ask_idea`, `quote_price`, `show_tattoo_slots`...). Это единственное
   место, где реально лежит бизнес-логика "что дальше" — она полностью
   покрыта юнит-тестами.
5. Если шаг требует слотов — подтягивается **календарь** (см. ниже),
   при подтверждении брони — реально бронируется.
6. **`getCardPatchForStep`** — что дополнительно записать в карточку из-за
   самого факта, что клиенту отдан этот шаг (например `ask_social` сразу
   ставит `social_asked='yes'`, не дожидаясь ответа).
7. Карточка сохраняется в Airtable.
8. **Responder** (LLM) пишет живой текст клиенту для этого шага.
9. При необходимости — пинг мастеру в личку (бронь, скрин оплаты, второй
   проект, перенос и т.п.).

Admin-сообщения (от `MASTER_TELEGRAM_ID`) перехватываются в начале и уходят
в отдельный `lib/admin.ts`, не через этот пайплайн — если только сама мастер
не переключилась в тестовый режим `/client`.

## Карточка клиента и несколько проектов

`ClientCard` (тип в `lib/stateMachine.ts`) — это все известные факты об
**одном проекте**. Обычно у клиента одна строка на `telegram_id`. Но клиент
может завести вторую, независимую татуировку, пока первая уже забронирована
— тогда:

- вторая татуировка получает **свою собственную строку** в Airtable (тот же
  `telegram_id`, отдельный `record.id`) и бот ведёт её как обычного нового
  клиента — не просто пингует мастера и отступает;
- `pages/api/telegram.ts` при каждом сообщении смотрит **все** записи
  клиента (`findAllClientRecordsByTelegramId` + `resolveActiveProjects` в
  `lib/airtable.ts`) и решает, какую из двух активных сообщение продолжает
  — переиспользуя сигнал `is_new_project_request`, а не отдельный
  LLM-вызов на сравнение;
- третий одновременный проект не поддерживается — если сообщение не
  подходит ни к одной из двух активных записей, срабатывает старый
  простой механизм: `new_project_after_booking` / `second_project_flagged`
  — один пинг мастеру, без отдельного ведения.

Это специально ограниченный охват (максимум 2 проекта), а не недосмотр —
осознанное решение под реальную нагрузку мастера.

**`isProjectRecordClosed`** решает, что проект больше не "активен"
(заблокирован или клиент явно отказался) — важно: `lead_status` при отказе
**не меняется**, поэтому "закрыт" проверяется отдельно, не одним статусом.

## Campaign mode (рекрутинг/рекламные deep links)

Один бот принимает людей из разных кампаний через Telegram deep link
`t.me/inka_assistant_bot?start=<campaign_id>`. Это полностью отдельный,
config-driven флоу, не переиспользующий обычную тату-воронку:

- **`lib/campaigns.ts`** — конфиг кампаний. Новая кампания = новая запись
  в массиве (`id`, `title`, `offer`, `payment`, `required_info`,
  `optional_info`, `booking_mode`...), без правок `stateMachine.ts` или
  промптов.
- **`lib/campaignFlow.ts`** — generic state machine над конфигом:
  `routeCampaign` решает шаг (`campaign_intro` → `campaign_ask_field` ×N →
  `campaign_handoff` → `campaign_followup_chat`) чисто по тому, какие
  `required_info`/`optional_info` ключи уже есть в `campaign_collected`.
  Код не знает смысла конкретных полей, только их наличие.
- `pages/api/telegram.ts` распознаёт `/start <payload>` ДО Extractor-а,
  активирует кампанию на карточке (`activateCampaign`) и, если
  `card.campaign_id` задан, `getNextStep`/`getCardPatchForStep`
  (`lib/stateMachine.ts`) делегируют весь роутинг в `campaignFlow.ts` —
  обычная диагностика (idea→price→booking) и `pricingRules` для такой
  карточки вообще не выполняются.
- Extractor/Responder получают `active_campaign`/`campaign` в input и
  используют свои overlay-файлы (`campaignExtractorOverlay.txt`,
  `campaignResponderOverlay.txt`) — тот же паттерн, что v2-оверлеи ниже:
  overlay безусловно приклеен к промпту, но эффективен только когда
  campaign не null во входных данных конкретного вызова.
- Хранение: `campaign_id` (Single line text) + `campaign_data` (Long
  text, JSON — собранные поля и `handoff_sent`) в Airtable, тот же паттерн,
  что `dialog_history`. Переживает перезапуск serverless-функции.
- Два `booking_mode`, после сбора всех `required_info` (и однократного
  прохода по `optional_info`):
  - **`master_approval`** — бот ничего не бронирует, карточка получает
    `campaign_handoff_sent='yes'` и мастеру уходит отдельное уведомление
    (`buildCampaignHandoffNotification`); Responder явно не обещает
    клиенту, что он принят — решение за мастером.
  - **`self_book_slot`** — бот сам показывает и бронирует слот из
    ОТДЕЛЬНОГО тега `[КАМПЕЙН]` (см. календарь ниже) — переиспользует те
    же generic-поля карточки (`slot_options`/`chosen_slot_id`), что и
    обычная тату/консультация, но через свой пул, не смешиваясь с
    клиентскими ОКНО/ЧАТ. Пустой пул не блокирует разговор (`campaign_no_slots`
    + одноразовый пинг мастеру через `__no_slots_pinged`), а не зацикливается
    и не выдаёт себя за решение мастера. **Бронь при этом ПРЕДВАРИТЕЛЬНАЯ**:
    в кампании нет предоплаты (нет "мягкого замка", как в обычной
    тату-воронке), поэтому её роль играет личное подтверждение мастера —
    бот прямо говорит клиенту, что время придержано, но подтвердит/свяжется
    сама Аня, не бот.
  `color_texture` сейчас использует `self_book_slot`; конфиг с
  `master_approval` остаётся доступен для будущих кампаний, где решение
  всегда должно оставаться за мастером.
- `photo_of_placement` у `color_texture` — ОБЯЗАТЕЛЬНОЕ поле (не optional):
  Ане нужно реально увидеть кожу крупно, с близкого расстояния, прежде чем
  решать. Extractor смотрит на само фото (вижн) и засчитывает ответ
  (`campaign_field_answer='yes'`) только если кадр реально крупный и
  близкий — издалека/не в фокусе фото не принимается, бот просит переснять.
  Сама фотография (не только факт "фото было") пересылается мастеру сразу
  через `forwardTelegramMessage`, как только Extractor её принял как ответ
  на это поле — текстовая сводка в карточке несёт только `yes`, не
  заменяет реальный просмотр фото мастером.

## LLM-слой: три промпта + два "v2-оверлея"

Три роли, три файла-промпта:

| Роль | Промпт | Что делает |
|---|---|---|
| Extractor | `lib/extractorPrompt.txt` | сообщение → факты + сигналы |
| Responder | `lib/responderPrompt.txt` | шаг → живой текст клиенту |
| Admin | `lib/adminPrompt.txt` | свободный диалог с мастерой, /портрет |

**Непривычный момент**, о который легко споткнуться: у Extractor и Responder
есть вторые файлы — `lib/extractorContractV2.txt` и `lib/responderVoiceV2.txt`.
Это не альтернативные промпты, а **оверлеи**: код (`extractor.ts`,
`responder.ts`) склеивает основной промпт и v2-файл в один system-prompt,
причём v2-текст идёт вторым и явно объявляет себя приоритетнее более ранних
формулировок по тем же темам (например quote_price). Название "v2" не
означает "второй промпт" — это исторический след того, что бывший
контрибьютор (Codex) добавил партию новых правил (service_fit-гейт,
классификация фото, второй проект) поверх уже существующих файлов, не
переписывая их с нуля. Смотреть только `extractorPrompt.txt` без
`extractorContractV2.txt` — значит видеть неполную картину поведения.

`lib/pricingRules.txt` — прайс-логика (категории, матрица цен, факторы
трудоёмкости) — общий кусок текста, который **и** extractor-промпт, **и**
admin-промпт подставляют себе через `{{PRICING_RULES}}`
(`lib/pricingRules.ts`), чтобы не дублировать и не рассинхронизировать два
места, считающие одну и ту же цену.

`lib/openai.ts` — общая механика HTTP-вызова к OpenAI (все три роли зовут
её, промпты остаются каждый в своём месте).

## Что тестируется, а что — только руками/CI с секретом

Два разных вида проверки, не путать:

- **`npm test`** (`test/selftest.ts` + `test/stateContractV2.ts` +
  `test/campaignFlow.ts` + `test/campaignClientJourney.ts`, ~355 проверок) —
  чистая логика без сети: `getNextStep`, `getCardPatchForStep`,
  `mergeClientCard`, парсеры команд, календарные хелперы, `resolveActiveProjects`
  и т.п. Никаких LLM-вызовов, работает без ключей. Гоняется в CI на каждый
  PR и пуш в `main` (`.github/workflows/tests.yml`).
- **`npm run eval:price` / `npm run eval:dialog`** (`scripts/priceEval.ts`,
  `scripts/dialogEval.ts`) — **живые** вызовы модели по реальным промптам,
  проверяют не логику, а качество и надёжность формулировок (например: цена
  крупного проекта обязана явно звучать "за сеанс"). Требует
  `OPENAI_API_KEY`, гоняется в CI только при изменении промпт-файлов
  (`.github/workflows/price-eval.yml`, включая v2-оверлеи) или руками.
  Не проходит offline — это осознанное ограничение, не баг настройки.

`lib/*.txt`-промпты никак не проверяются `npm test` — их корректность
живёт только в `eval:*` и в реальном использовании. Если меняешь промпт,
но не гоняешь `eval:dialog` — правка не проверена никем и ничем, пока не
попадёт на прод.

## Календарь и слоты (`lib/calendar.ts`)

Пять тегов событий Google Calendar, из трёх разных источников — ключевое,
что нужно понять перед правками:

- **`[ТАТУ]` / `[ПРИЁМ]`** — реальные сессии мастера (вручную или синком из
  её Дневника). Бот их никогда не предлагает клиентам в чате, использует
  только для собственной ориентации (день занят / не занят).
- **`[ОКНО]` / `[ЧАТ]`** — теги, которые бот может предложить ОБЫЧНОМУ
  клиенту. Мастер заранее создаёт их пустыми (`/добавить`) как открытый
  пул, бот их бронирует по мере записи клиентов.
- **`[КАМПЕЙН]`** — отдельный открытый пул для рекрутинг/рекламных
  кампаний (см. выше, `booking_mode: self_book_slot`). Технически работает
  как `[ОКНО]`/`[ЧАТ]` (`/добавить кампейн ...`, `getAvailableSlots('campaign', ...)`,
  `bookSlot(..., 'campaign', ...)`), но это полностью отдельный пул — у
  него нет Дневник-тега и он никогда не предлагается обычным клиентам и
  наоборот. `SlotFamily`/`SlotTag` в `lib/calendar.ts` знают про него
  как про третью, самостоятельную семью.

`lib/addSlotParser.ts` — детерминированный (без LLM) разбор команды
`/добавить`/`/закрой`/`/удали`: ошибка в дате/времени реального слота — это
не опечатка в тексте, а неправильный слот, который увидят клиенты, поэтому
здесь сознательно нет угадывания моделью.

## Дневник мастера (отдельное приложение, не часть этого репо)

- `pages/api/diary-sync.ts` — Дневник → сюда → тот же Google Calendar, что
  читает бот. Доступ по секрету `DIARY_SYNC_SECRET`.
- `pages/api/bot-bookings.ts` — обратный поток, только на чтение: список
  броней/блокировок/открытых слотов бота, чтобы мастер видела их в Дневнике
  и сама заводила карточку клиента там вручную. Бот карточки в Дневнике не
  создаёт и не трогает.

## Cron-джобы (Vercel Cron, см. `vercel.json`)

Все три работают **по расписанию**, не по сообщению клиента, и все читают
Airtable **по записям** (через `record.id`), а не по одной записи на
`telegram_id` — поэтому у клиента с двумя активными проектами каждый
корректно сработает независимо для каждой строки:

- `payment-reminders.ts` — два независимых окна (позднее ≤36ч до слота,
  раннее ≥N часов после брони), каждое со своим guard-полем.
- `warm-lead-reminders.ts` — цену показали, ответа да/нет так и не было,
  клиент молчит достаточно долго.
- `waiting-list-check.ts` — единственный cron, который пишет **клиенту**
  напрямую (остальные только пингуют мастера): если для его типа (тату/
  консультация) появились слоты, пока он был в листе ожидания.

Общая временная логика (когда именно считать "пора") вынесена в
`lib/reminderWindows.ts` — чистые функции, покрыты тестами, сами
`pages/api/*.ts` — нет (завязаны на сеть).

## Переменные окружения

| Переменная | Для чего |
|---|---|
| `AIRTABLE_TOKEN`, `AIRTABLE_BASE_ID`, `AIRTABLE_TABLE_ID` | хранение карточек клиентов |
| `TELEGRAM_BOT_TOKEN` | сам бот |
| `OPENAI_API_KEY` | Extractor / Responder / Admin |
| `GOOGLE_SERVICE_ACCOUNT_EMAIL`, `GOOGLE_PRIVATE_KEY` или `GOOGLE_SERVICE_ACCOUNT_JSON` | доступ к календарю |
| `DIARY_SYNC_SECRET` | авторизация запросов от Дневника мастера |
| `CRON_SECRET` | авторизация вызовов cron-эндпоинтов |
| `PAYMENT_DEPOSIT_AMOUNT`, `PAYMENT_BIT`, `PAYMENT_BANK` | сумма и реквизиты предоплаты, единая точка правды (`lib/paymentConfig.ts`) |
| `PING_MASTER_ON_ALL_MESSAGES` | опционально: пинговать мастеру вообще каждое сообщение клиента (отладка) |

## Известные ограничения (не баги — сознательные компромиссы или открытый долг)

- **Максимум 2 параллельных проекта на клиента.** Третий — просто пинг
  мастеру без полноценного ведения (см. выше).
- **Маршрутизация между двумя активными проектами — эвристика, не
  гарантия.** Экстрактору дают краткую сводку второго проекта
  (`otherActiveProject` в `lib/extractor.ts`), а не полноценное сравнение
  двух карточек — по-настоящему двусмысленное сообщение иногда может уйти
  не туда.
- **Гонка при двух почти одновременных сообщениях** может теоретически
  создать два дубля для второго проекта (нет блокировки на уровне
  Airtable-записи). Тот же класс риска есть и у совсем нового клиента при
  `upsertClient` — не специфично для второго проекта, просто ещё не решено
  нигде в проекте.
- **`.txt`-промпты не покрыты `npm test`.** Единственная защита — живой
  `eval:dialog`/`eval:price`, который надо не забыть прогнать (CI это
  теперь делает автоматически при изменении промпт-файлов, включая v2).
